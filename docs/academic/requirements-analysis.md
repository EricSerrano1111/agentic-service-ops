## **Introduction**

The Agentic Service Operations Intelligence Platform is a multi-agent AI system built on a simulated enterprise field service operations environment. This simulated field service organization captures dispatching technicians, tracking billing, and managing quality incidents and customer feedback across thousands of service requests. The system lets an operations user ask a natural language question and receive a verified answer, without writing SQL, learning new technical skills, or waiting on an analyst.

**The platform incorporates four architectural components working together:**

- **Orchestrator:** that classifies user intent and routes each request to the appropriate specialist agent.
- **Three specialist agents**: each restricted to its own narrowly scoped data access.
  - Reporting (incident/quality metrics)
  - Sentiment (customer feedback classification)
  - Forecast (service volume prediction)
- **QA agent:** that independently verifies each specialist's output before it reaches the user, with the authority to reject and trigger revision rather than passing unverified results through.
- **A protocol and security layer**: Agent-to-Agent (A2A) for orchestrator to specialist coordination, Model Context Protocol (MCP) for each agent's tool access, and per agent least privilege database roles enforcing that no agent can reach data outside its domain.

The system is deployed as containerized services on Google Cloud Platform, with a web interface over a FastAPI gateway.

### **Current State vs Future State Assessment**

**Current State**

Meridian Field Services dispatches technicians for network and hardware installs, repairs, maintenance, and upgrades. As service volume has grown, so has the operational data generated: completed jobs, quality incidents, customer feedback, and demand patterns across regions and skill categories.

Today, answering any operational question about that data as in quality trends, customer sentiment, demand forecasting, requires either a data analyst manually pulling and interpreting numbers, or an operations leader attempting the extraction themselves. Both paths are slow relative to how frequently these questions arise, and neither are scalable with continued growth.

Leadership has signaled a preference for scaling analytical capability without scaling analyst headcount, but no mechanism exists today for operations staff to get answers directly. The practical result is that day to day decisions are frequently made on intuition or stale reporting, and the analysts who could answer precisely have become a bottleneck rather than a resource.

**Future State**

With the platform implemented, an operations leader asks a plain-language question about incident patterns, customer sentiment, or forward demand, and receives an answer within minutes, with no analyst in the loop for routine queries.

Every answer is independently verified by a dedicated QA stage before it reaches the user, so the answer can be acted on directly rather than treated as a starting point for a follow up conversation with the analyst team. Because the system scales by adding data rather than by adding headcount.

Meridian's analytical capacity grows in proportion to service volume without a corresponding analyst hire.

## **Assumptions**

**Business context and scope**

- **A-01.** Meridian Field Services is a representative, fictional organization. Its business problem reflects the common situation of field service operations that rely on analysts for operational reporting.
- **A-02.** Users are operations leaders asking questions in English, one question at a time, within the three supported domains: incident and quality reporting, customer sentiment, and service volume forecasting.
- **A-03.** The system only reads operational data. No agent creates, changes, or deletes records.
- **A-04.** User accounts and per-user permissions are out of scope. Access to the deployed system is limited to authorized users (the developer, the instructor, and demo audiences) through the access control in Security requirement 2.

**Data**

- **A-05.** All data is synthetic, generated from documented parameters (seasonality, growth trend, incident rates, sentiment mix, injected anomalies). Accuracy results show how well the system recovers known patterns, not how it would perform on any real company's data.
- **A-06.** The dataset is static for the duration of the project. In a real deployment, the system would connect to the organization's live operational database, integrating with a live data source is out of scope.
- **A-07.** Synthetically generated customer feedback, once checked by sampling against its intended sentiment, is realistic enough to train and evaluate the sentiment model. Its known limitations are reported, not hidden.

**Technology and external dependencies**

- **A-08.** The Gemini API free tier remains available with its current rate limits (15 requests per minute and 500 per day for Flash-Lite) through the end of the project. If pricing or access changes, the provider-agnostic model interface allows switching providers without changing the orchestration layer.
- **A-09.** Full evaluation runs may exceed the free tier's daily limit. They will be split across days or run on a separate paid project with a spending cap.
- **A-10.** The MCP (2026-07-28 specification) and A2A (v1.0) software libraries remain stable enough to use. Versions are pinned at project start and not upgraded mid-build without a specific reason.
- **A-11.** Google Cloud free tiers and existing credits, together with a personal budget of roughly \$100 USD, cover hosting, the database, and model usage. The managed cloud database is used only from Sprint 5 onward.

**Project constraints**

- **A-12.** The project is built by one developer.
- **A-13.** The final product is due December 5, 2026, the end of Module 10. The six two-week sprints run from mid-September to that date, so the sprint plan and the course deadline align.
- **A-14.** Requirements marked "No" in the MVP column (FR-20 to FR-22) are not contracted deliverables. If time allows any of them to be built, they are delivered as additions, not obligations.

**Database Notes**

- **This is a simplified view.** The ERD and relationship table show tables, keys, and relationships only. The full schema, including every column, allowed values, and constraints, is maintained in the project's data dictionary and is available on request.
- **All data is synthetic.** Every record is generated from documented parameters (seasonal demand, growth trend, incident rates, sentiment mix, and a small number of deliberate anomalies), with a saved random seed so the dataset can be reproduced exactly. Contact details use reserved formats, such as 555-01xx phone numbers and example.com email addresses, so nothing resembles a real person.
- **Planned scale:** 36 months of history, roughly 15,000 to 25,000 service requests, about 7,200 customer feedback responses, 40 to 60 client accounts, and 25 to 40 technicians.
- **Incidents and feedback are separate tables on purpose.** Customers are surveyed after every completed job, and most jobs go well, so feedback covers the full range from positive to negative. Incidents are internal quality records written by staff. Keeping them apart gives the sentiment agent a realistic mix of feedback and keeps staff notes out of customer sentiment results.
- **Some rules are enforced by the database, others by validation.** The database enforces keys, relationships, and value checks (for example, ratings must be 1 to 5 and charges cannot be negative). Rules that span tables, such as "every completed request has exactly one billing record" and "every feedback response has a sentiment label," are checked by data validation after generation and by the QA agent at runtime.
- **Some figures are calculated, not stored.** Invoice totals, whether a request met its service-level target, and first-time fix rate are calculated when requested, using one fixed definition for each. This keeps the reporting agent and the QA agent from disagreeing because a stored value went stale.
- **Service-level targets are recorded at the time of the request.** If a client later moves to a different contract tier, its past requests are still judged against the targets that applied when they were made, so historical reports don't change.
- **The two ground-truth tables are for evaluation only.** sentiment_labels holds the intended sentiment of each feedback response, and generation_parameters holds the settings used to create the data. The QA agent uses them to verify results. No specialist agent can read them (see Appendix A).
- **Conventions:** all times are stored in UTC, all amounts are in US dollars, and records are corrected rather than deleted.
- **Platform:** PostgreSQL, run locally during development and on Google Cloud SQL once the system is deployed, with identical schema migrations in both environments.
