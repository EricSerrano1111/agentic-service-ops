## Criteria

Each criterion says what "met" means at this project's scale: a solo, six-sprint capstone on Cloud Run with a roughly $100 budget (`architecture.md` §9). Verdict vocabulary (applied in the evidence commit): `Met, deployed` · `Met, offline only` · `Partly met` · `Deferred` · `Not met`.

Where §7's wording is vague, the reading chosen is stated. §7 itself says an item may be "explicitly scoped out with a documented reason"; a verdict of `Deferred` needs that reason in a record, not in this audit.

### 1. Containerized services, reproducible builds

- **Criterion.** Every deployable service (gateway, orchestrator, three agents, QA, and the three MCP servers) builds from its own Dockerfile in a clean checkout, runs in the local compose stack, and runs on Cloud Run from the image the build produced. "Reproducible" is read as **dependency reproducibility**: every Python dependency is installed from the committed `uv.lock` (`--locked`), the same lock feeds CI and the images, and the deployed image is identifiable by the commit it was built from (tag = commit SHA). It is **not** read as bit-for-bit identical images, and it does **not** require base images pinned by digest. Reason: §7 says "reproducible builds", the ADR that pins dependencies (ADR-047) is about the lock, and digest-pinning is a supply-chain hardening a solo capstone does not need. If base images turn out to be floating tags, that is reported as a limit on the verdict, not as a failure of the criterion.
- **Required or portfolio.** Required. Containers are the unit of deployment on Cloud Run (ADR-045, ADR-079). The digest-pinning stricter reading would be portfolio, and is not applied.

**Verdict: Met, deployed.**

**Evidence.**
- All nine Dockerfiles install with `uv sync --locked --no-dev --no-editable` against the committed `uv.lock`, with uv pinned to 0.12.19 (by search: `services/*/Dockerfile`, for example `services/orchestrator/Dockerfile:10` and `:19`). CI installs the same way and fails on a stale lock (`.github/workflows/ci.yml:32-35`, `:54-57`, `:116-119`).
- Images are tagged by commit: `deploy/cloudbuild.yaml:47` (`orchestrator:${COMMIT_SHA}`) and the equivalent lines for the other builds.
- Deployed, not just built: `gcloud builds describe 0dc5aae1-2a6c-498e-bbca-f709c2c91149 --region us-central1` (read 2026-10-16T22:50Z) gives `status: SUCCESS`, `COMMIT_SHA: 9ab7c775964bd0aae491ca72082e95229c994129`, finish 2026-10-15T01:33:28Z. All nine containers of the six serving services carry the tag `9ab7c775964bd0aae491ca72082e95229c994129` (appendix, read 2026-10-16T22:47:31Z).
- Image hygiene is tested: `test_final_stage_runs_as_a_non_root_user`, `test_no_credentials_are_baked_into_the_image`, `test_dockerignore_is_an_allowlist_that_keeps_env_files_out` (`tests/unit/test_dockerfiles.py`).
- Runs under compose: `docker-compose.yml` defines the full stack; in the fresh clone `docker compose config -q` passes once the model key has a value (section 3 record). The stack itself was not started in this audit (Docker Desktop was not running). Its earlier local run is recorded in the Z2a proof (`docs/sprint-log.md`, Sprint 6, "Proof of no answer change", 2026-10-14).

**Gaps and limits.** Base images are floating tags (`python:3.12-slim`; `node:24-slim` at `services/api_gateway/Dockerfile:11`; `postgres:16` in CI; by search), not digests. Under the chosen reading that is a limit, not a failure. Two builds of the same commit are not promised to be byte-identical. `mcp_feedback` has two build targets (`stored` and `full`); the deployed one is `stored` (ADR-100).

### 2. Config and secrets management: no hardcoded credentials

- **Criterion.** No credential value is committed or baked into an image; configuration comes from the environment. On the deployed system, each secret lives in Secret Manager and is mounted only into the container that needs it, and no secret value appears in logs. Locally, credentials come from the gitignored `.env`, and a test or check guards against literals in deployed files. "No hardcoded credentials" is checked by search of the repository and by the existing guard tests, not by a full history scan (secret scanning on pushes is outside §7 and is listed in the outside-the-checklist section).
- **Required or portfolio.** Required (ADR-028 and ADR-079 make it a design rule, not a flourish).

**Verdict: Met, deployed.**

**Evidence.**
- Mounts, read from the deployed services (appendix, 2026-10-16T22:47:31Z): each database password is mounted in exactly one container, the MCP sidecar of its service (`DB_ROLE_REPORTING_PASSWORD` in `mcp-incidents`, `DB_ROLE_SENTIMENT_PASSWORD` in `mcp-feedback`, `DB_ROLE_FORECAST_PASSWORD` in `mcp-volume`). The one exception is `DB_ROLE_QA_PASSWORD` in `agent-qa`, which has no sidecar by design (ADR-089; `test_agent_qa_holds_only_app_qa_credentials_and_no_volumes`). The two Gemini keys are mounted in the five model-calling containers only. The gateway holds `GATEWAY_SESSION_KEY`. No sidecar and not the gateway holds a model key.
- Guard tests in CI: `test_secrets_go_only_to_the_containers_that_need_them` (`tests/unit/test_deploy_config.py:107`), `test_no_sidecar_and_not_the_gateway_is_in_paid_mode_or_holds_a_model_key` (`:155`), `test_no_public_invoker_and_no_real_identifiers_in_the_drafts` (`:214`); `test_no_deployed_file_references_offline_role_credentials` (`tests/unit/test_offline_roles_isolation.py:69`); `test_no_secret_literals_in_compose` and `test_no_service_gets_the_paid_key` (`tests/unit/test_compose_isolation.py`, compose only). `.env` is ignored (`.gitignore`, by search).
- No secret in the logs, deployed and current: a read-only pattern search of the Cloud Run `stdout` log over the last 14 days (2026-10-16T23:06Z) for `AIza`, `Bearer `, `eyJ`, `postgresql://` and `password=` returned 0 entries for each. This is pattern-based and cannot test exact secret values (reading Secret Manager values is out of scope here). A positive control with the same query shape, for the term `ask received`, returned 20 entries (the limit), so the quoted-term filter does work (2026-10-16T23:17Z). Cloud Run's own request log (`run.googleapis.com/requests`) was also read, because it records request URLs: the 15 `/auth/exchange` entries in 14 days are all `POST` with no query string, none of the sampled request URLs contains `token=`, and the sampled paths are `/ask`, `/api/ask`, `/` and `/api/session`. So the invite token is not in a logged URL. It supplements the 2026-10-08 exact-value scan: 281 entries, five secret values, 0 findings (`docs/deploy-window-log.md`, "Step 10: log scan"), which covered two services on an earlier build.

**Gaps and limits.** No full git-history scan (outside the checklist; section 4). The log scan is pattern-based (L-63); a secret with no recognisable pattern would not be found. `security-model.md:264` says "LLM callers get only the free key; no service gets the paid key", which is true of compose and false of the deployed system (`security-model.md:271` and ADR-104 state the deployed case). See finding F7.

### 3. Structured logging with trace IDs correlated across agent hops

- **Criterion.** Every service writes JSON log lines through one formatter. One trace ID is minted or accepted at the entry point and appears on the log lines of every hop of a request: gateway, orchestrator, A2A agent, MCP server and QA agent, including web-server access lines (ADR-108). Met on the **deployed** system means a read of Cloud Logging shows one trace across more than one service. Logging the question text or secrets is a limit on the verdict, not a failure of "structured" or "correlated"; the redaction gaps are stated as limits (L-98 and the L-60 remainder).
- **Required or portfolio.** Required. Without it a failure across seven processes cannot be diagnosed (ADR-108).

**Verdict: Met, deployed.**

**Evidence.** One request, trace `29972a2583864f62ba8de223c1092291` (owner session 1, TS-20-A, 2026-10-15 19:03 CDT), read from Cloud Logging at 2026-10-16T22:50:27Z with `jsonPayload.trace_id="29972a25..."`. It returns 22 entries from four services, in order:
- `ops-orchestrator`: `ask received`, `llm call`, `route decision`, then later `qa verdict`, `ask answered`, `request /ask 200`;
- `ops-reporting`: the agent-card fetch `request`, `task received`, `llm call`, `question parsed`, then the `mcp_incidents` sidecar's `tool call` and two `request /mcp 200` lines, `task completed`, `request / 200`;
- `ops-qa`: the agent-card fetch, `task received`, `llm call`, `interpretation judged`, `task completed`, `request / 200`;
- `ops-gateway`: `ask answered` and `request /api/ask 200`.

So the trace ID is on the gateway, the orchestrator, the A2A agent, its MCP sidecar and QA, and on the web-server access lines (`msg=request`, with `path` and `status`). Two more session-1 traces, read the same way: `2d737c70bc794769b86fae26b58cb028` (sentiment: 9 sentiment, 6 QA, 6 orchestrator, 2 gateway entries) and `d0f1971e98f74227a0172b22292e01f0` (forecast: 9, 6, 6, 2). Offline: `tests/unit/test_trace_access_log.py`, `services/orchestrator/tests/test_trace_id_header.py`, `services/api_gateway/tests/test_gateway_trace_id.py`. One formatter: `packages/common/src/common/logging.py`. ADR-108.

**Gaps and limits.** L-98, as `security-model.md` section 5's 2026-10-16 update states it: tool error text, including dates parsed from the question, can appear in two services' logs (`agent_reporting`'s `task failed` line and `mcp_incidents`); question wording was not seen in the logs; only one failure path was checked live (`invalid_range`, trace `2e3dc32a...`, session 1). The L-60 remainder also stands: Google's own error sentence for a rejected request is still logged (capped), and QA, sentiment and forecast have no end-to-end name test of their own. `outcome=degraded` from a real fault on the current build has not been exercised (item 6).

### 4. Health checks and readiness probes on every service

- **Criterion.** Every service exposes a liveness endpoint (`/healthz`), and every service that has a dependency (an agent's MCP sidecar, an MCP server's database) exposes a readiness endpoint (`/readyz`) that checks it. "Readiness probe" is read for Cloud Run, which has **startup and liveness probes, not a separate readiness probe**: the criterion is a startup probe on every container that gates on `/readyz` where a dependency exists, plus the endpoints for liveness. §7 says "every service", so the gateway, orchestrator and QA agent are in scope. A configured Cloud Run `livenessProbe` is **not** required by §7's wording; if absent it is stated as a limit, and as a finding if a doc claims otherwise.
- **Required or portfolio.** Required: the sidecar start-up ordering depends on it (ADR-079).

**Verdict: Partly met.** Criterion part (a), the endpoints, is met. Part (b), the startup probe gating on `/readyz` where a dependency exists, fails for one container.

**Evidence.**
- (a) Liveness endpoints: `/healthz` on all nine HTTP servers (by search of `services/*/src/*/app.py` and `server.py`; for example `services/orchestrator/src/orchestrator/app.py:412`, `services/agent_qa/src/agent_qa/app.py:69`). The gateway also serves `/health` publicly, because Cloud Run reserves `/healthz` on its front end (`services/api_gateway/src/api_gateway/app.py:225`; `docs/decisions-log.md:3181`).
- (a) Readiness endpoints where a dependency exists: `/readyz` on the three agents (their MCP server answers), the three MCP servers (the database answers) and QA (the database answers as `app_qa`, `services/agent_qa/src/agent_qa/app.py:73`). Tests: `test_readyz_ready_when_the_mcp_server_answers` and `test_readyz_not_ready_when_the_mcp_server_does_not_answer` (each agent), `test_readyz_not_ready_when_the_database_is_unreachable_and_leaks_nothing` (each MCP server), `test_healthz_always_answers_and_readyz_reflects_the_database` (QA). The orchestrator and gateway have no `/readyz` (by search). Under the chosen reading they have no sidecar or database dependency, so they need liveness only.
- (b) Deployed startup probes (appendix, 22:47:31Z): all nine containers have one. The three agents with a sidecar and the three MCP sidecars probe `/readyz`, and each agent waits for its sidecar (`run.googleapis.com/container-dependencies`; `test_the_agent_waits_for_a_sidecar_whose_probe_is_its_readiness_endpoint`). Proven on Cloud Run on 2026-10-08: with the database stopped, the sidecar's `/readyz` failed 20 times, Cloud Run refused the revision and no traffic moved (`docs/deploy-window-log.md:85` and `:128`; reporting slice only).
- **The gap.** The deployed `ops-qa` agent container probes `/healthz`, not `/readyz` (`deploy/cloudrun/qa.yaml:79-82`; confirmed on the running service at 22:47:31Z). QA has a database dependency and a `/readyz` that checks it, and that endpoint's docstring says "Startup probes point here" (`services/agent_qa/src/agent_qa/app.py:74`). A QA revision can therefore start and take traffic with the database unreachable. Criterion (b) requires the probe on `/readyz` here.
- **No `livenessProbe` is configured on any of the nine containers** (by `describe`; none under `deploy/` by search). The criterion does not require one. §7's text, "`/healthz` liveness on every service", is true of the endpoints and not of the Cloud Run configuration.

**Gaps and limits.** The QA probe (F1). The missing liveness probes (F2): a hung but started instance is not restarted by a probe. The 2026-10-08 refusal proof predates the six-service deploy and was not repeated for QA.

### 5. Bounded retries, timeouts and circuit breaking on all inter-agent calls, within the 120-second ceiling

- **Criterion.** "All inter-agent calls" is read as: orchestrator to each specialist agent (A2A), orchestrator to QA, and the model transport (Gemini) called by the orchestrator, agents and QA. It does **not** include an agent's call to its own MCP sidecar over localhost, which carries no network risk of the same kind (ADR-079); if that call has a timeout anyway, it is noted. Met requires: one request deadline passed through every hop; a per-hop timeout that fits inside 120 s; a bounded retry; a breaker per specialist and for QA and the model transport; a bounded revision loop; and a defined result when a bound is hit. **Deployed** evidence means a bound or breaker was seen to act on Cloud Run; code and tests alone make the item `Met, offline only`. Retry *logging* is a separate sub-claim and is judged on its own evidence.
- **Required or portfolio.** Required for the 120 s ceiling and the NFR it serves (ADR-077, ADR-088); the breaker is deliberately minimal (ADR-077 titles it "minimal").

**Verdict: Met, offline only.** Parts have deployed evidence (below). The full criterion, every bound and breaker acting on Cloud Run, does not.

**Evidence.**
